# План MILEAGE: пробег > 400 000 км → решение review

Задача: в расчёт решения по заявке добавить проверку «пробег авто не больше
400 000 км, иначе решение `review`».

Основа — `docs/setup/code_map.md`, разделы 2–3 (обзор всего, что связано
с пробегом), перепроверено по текущему коду 2026-09-24: номера строк
актуальны, других проверок пробега нет. После валидации `mileage` только
пробрасывается в `$input`, ответ и БД (`vehicles.mileage_km`); в
`DecisionEngine`, `LtvCalculator`, `VehicleAge`, `VinValidator` пробега нет.
Единственное место, где рождается decision, — `DecisionEngine::decide()`
(`DecisionEngine.php:30`), туда правило и встраивается.

Допущения плана (если заказчик ответит иначе — см. Вопросы, правится до кода):

- «Не больше 400 000» = `mileage <= 400000` проходит, `400001` → review.
- Пробег только **понижает** `approve` до `review` и не «повышает» `reject`
  до `review` (по code_map, раздел 2): проверка живёт внутри approve-ветки,
  `reject` по LTV при любом пробеге остаётся `reject`.

## 3. Тесты

Граничные значения пробега — `tests/Unit/DecisionEngineTest.php`, LTV в

- `mileage 399999` → `approve`
- `mileage 400000` → `approve` (граница «не больше»)

Приоритет правил (пинируют допущение из шапки, зависят от ответа на Q1):

- LTV 95.0 (зона reject) + `mileage 400001` → `reject`, а не review
- LTV 72.3 (зона review) + `mileage 400001` → `review`
- LTV 72.3 (зона review) + `mileage 399999` → `review` (низкий пробег не «спасает»)

Совместимость с валидацией — `tests/Unit/ApplicationValidatorTest.php`
(валидатор не меняется, пинируем существующее поведение):

- `mileage 500000` → валидацию проходит, заявка доходит до решения
- `mileage 500001` → `ValidationException` (потолок `max_mileage_km` не тронут)

  `ValidationException` с ключом `mileage` и текстом «Пробег от 0 до 500000 км»,

- нюанс для теста или явной пометки: `mileage: null` или `""` приводятся к 0 и
  валидацию проходят — при низком LTV это approve «с неизвестным пробегом»
  (сегодняшнее поведение; см. Q3, не менять до ответа)

- LTV 50.0 + `mileage 400000` → `approve`, `approved_limit` = запрошенная сумма

## 4. Риски

- **Вилка с `max_mileage_km` (главный риск)**: появляются два порога —
  400001…500000 теперь зона `review`, больше 500000 остаётся ошибкой валидации
  (422, до решения не доходит). Риск перепутать пороги при будущих правках:
  новый ключ лежит рядом в `vehicle`, с комментарием; обе границы пинированы
  тестами (400001, 500000, 500001). Сам `max_mileage_km = 500000` не менять —
  это риск-параметр, его изменение только по явному решению риск-менеджмента.
- **Приоритет reject/review**: буквальное чтение задачи («иначе решение review»)
  даёт review и при reject-LTV; план исходит из «пробег только понижает
  approve». Если ревью/интервью выберет буквальное чтение — проверка
  переезжает в начало `decide()` до LTV-веток и переписываются тесты
  приоритета. Согласовать до кода (Q1), не подгонять потом тесты под код.
- **Слом сигнатуры `decide()`**: вызовов два — `AssessmentService.php:33` и
  `DecisionEngineTest.php:23`, моков двигателя нет, правка механическая, но
  до обновления тестов `make test` красный.
- **Пустой/неизвестный пробег**: `null`/`""` → 0 → возможен approve без
  известного пробега. Менять валидатор до ответа заказчика нельзя (Q3).
- **Лимит при понижении**: approve → review обязан гасить `approved_limit` в 0 —
  в `AssessmentService.php:39` это получается автоматически, но кейс пинируется
  сквозным тестом, чтобы будущий рефакторинг не сломал.
- **Дальше по цепочке**: задача LOAN-12 (лимит по `ltv_by_age`) будет строиться
  на `decide()` — сигнатуру меняем сейчас одним разом, LOAN-12 возьмет готовую.
- **Seed/БД не страдают**: все засеянные пробеги ≤ 296000 (`seed.sql:31–55`),
  противоречащих новому правилу сохранённых решений нет; миграций, правок
  `schema.sql`/`seed.sql` не нужно.
- **Не входит (scope)**: пороги LTV и их известное расхождение docblock «<=»
  vs код «<» при LTV ровно 60 (`code_map.md`, п. 1) не трогаем — отдельная
  история; фронтенд не меняем (решение приходит с сервера, дублировать пороги
  в JS не нужно); VIN-сервис и залоговая стоимость (CASE-08) — другая задача;
  новых эндпоинтов и полей ответа нет.

## Вопросы, на которые без заказчика не ответить

- **Q1. Приоритет**: LTV даёт `reject`, пробег 400001 — финал `reject`
  (допущение плана: пробег только понижает approve) или `review` (буквальное
  «иначе решение review»)? От ответа зависит место проверки в `decide()`.
- **Q2. Вилка порогов**: диапазон 400001–500000 становится зоной review,
  а выше 500000 остаётся ошибкой валидации. Это желаемое поведение, или
  заказчик ожидает другую обработку верхней границы (`max_mileage_km`)?
- **Q3. Пустой пробег**: отсутствие поля — ошибка валидации (422, сегодня
  так), но `null`/пустая строка превращаются в 0 и могут дать approve.
  Считать ли «неизвестный пробег» поводом для review или ошибки? Меняет
  валидатор, вне этого плана.
- **Q4. Граница**: «не больше 400 000» — это `400000` ещё approve (допущение
  плана) или граница строгая (`400000` уже review)? Пинируется тестом.
