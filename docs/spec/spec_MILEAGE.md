# Spec MILEAGE: пробег не больше 400 000 км, иначе решение review

Задача: `MILEAGE`. Дата: 2026-10-01. Источник: `docs/intent/intent_MILEAGE.md`,
лог интервью `docs/intent/grill_MILEAGE.md`. Все числа учебные и синтетические.

Это спецификация «что считается сделанным»; реализация — в `docs/plan/`.

## 1. Входит

- Проверка пробега в расчёте решения по заявке: при пробеге выше порога
  результат решения понижается до `review` (источник: intent §1,
  формулировка задачи).
- Порог пробега — 400 000 км (источник: intent §3, ответ в интервью,
  `grill_MILEAGE.md` в. 1).
- Диапазон действия новой проверки — пробег от 400 001 до 500 000 км
  включительно: пробег свыше 500 000 км — по-прежнему ошибка валидации и до
  расчёта решения не доходит (источник: intent §3, `grill_MILEAGE.md` в. 5,
  `backend/config/rules.php:23` `vehicle.max_mileage_km = 500000`).
- Сохранение сегодняшних LTV-порогов решения как основы: `approve` при
  LTV < 60, `review` при 60 ≤ LTV ≤ 85, `reject` при LTV > 85 (источник:
  intent §3, `backend/config/rules.php:44-45`, `backend/src/Domain/DecisionEngine.php:32-40`).
- Лимит по заявке выдаётся только при `approve`; при `review` и `reject`
  лимит равен нулю (источник: intent §3,
  `backend/src/Domain/AssessmentService.php:39`).
- Поведение проверки на границах пробега 399 999 / 400 000 / 400 001.

## 2. Не входит

- Нормализация «неизвестного» пробега (`null` / пустая строка как отдельное
  состояние): в интервью решено «неизвестный → review»
  (`grill_MILEAGE.md` в. 2), но реализация вынесена в отдельную задачу
  (`grill_MILEAGE.md` в. 6, intent §5). До этой отдельной задачи в MILEAGE
  approve с `null`-пробегом временно остаётся возможен, потому что сегодня
  `null`/пустая строка приводятся к 0 и проходят валидацию
  (`backend/src/Domain/ApplicationValidator.php:43-46`).
- Изменение потолка валидации `max_mileage_km = 500 000` — риск-параметр не
  меняется (источник: `grill_MILEAGE.md` в. 5, ответ заказчика).
- Изменение LTV-порогов `approve_max = 60.0` и `review_max = 85.0` — это
  риск-параметры, не меняются (источник: `backend/config/rules.php:44-45`,
  intent §3).
- Что-либо, не относящееся к проверке пробега в расчёте решения (источник:
  intent §5, исходная формулировка задачи).

## 3. Термины и состояния

- `mileage` — целое число километров в заявке. Диапазон валидации —
  0…500 000 включительно (источник: `backend/src/Domain/ApplicationValidator.php:43-46`,
  `backend/config/rules.php:23`).
- Решения — строки: `approve`, `review`, `reject` (источник:
  `backend/src/Domain/DecisionEngine.php:16-18`).
- LTV — loan-to-value, проценты, `запрошенная_сумма / оценочная_стоимость *
  100` (источник: `backend/config/rules.php:36-46`).

## 4. Требования

### REQ-MILEAGE-01 — порог проверки пробега в расчёте решения

В расчёте решения по заявке присутствует порог пробега 400 000 км. При
пробеге выше этого порога (то есть > 400 000) результат решения —
`review`. Это требование фиксирует само наличие правила и его числовое
значение; конкретное поведение на границе и приоритет с `reject` —
отдельные требования ниже.

Источник числа 400 000: `intent_MILEAGE.md:24` («Порог — 400 000 км —
ответ в интервью»); `grill_MILEAGE.md:9` (в. 1).

### REQ-MILEAGE-02 — граница 400 000 км

При пробеге ровно 400 000 км результат решения по заявке — `approve`,
если LTV-заявка попадает в approve-зону; правило пробега не понижает
решение при пробеге ≤ 400 000 км.

Источник: `intent_MILEAGE.md:24-25` («Поведение на границе "ровно
400 000" — открытый вопрос»), допущение плана в
`grill_MILEAGE.md:17` («400 000 → approve, 400 001 → review»), статус
в `grill_MILEAGE.md:77` («до решения: 400 000 → approve»), владелец —
риск-менеджмент. До решения риск-менеджмента это поведение пинируется
тестом и может быть изменено отдельным изменением спеки.

### REQ-MILEAGE-03 — пробег выше 400 000 км переводит approve в review

Если LTV-заявка попадает в approve-зону (LTV < 60), но пробег строго
больше 400 000 км, результат решения по заявке — `review`, а не
`approve`.

Источник: `intent_MILEAGE.md:7-10` («пробег не больше 400 000 км —
решение не меняется; иначе — решение review»),
`grill_MILEAGE.md:77` (сводка «Неизвестный пробег / Приоритет с reject»).

### REQ-MILEAGE-04 — пробег не поднимает review выше

Если LTV-заявка попадает в review-зону (60 ≤ LTV ≤ 85), пробег не
меняет результат: решение остаётся `review`. Это требование фиксирует,
что правило пробега только понижает результат решения и не повышает его.

Источник: формулировка «иначе — решение review» в
`intent_MILEAGE.md:7-10`: review уже `review`, повышать некуда.

### REQ-MILEAGE-05 — reject не перекрывается пробегом

Если LTV-заявка попадает в reject-зону (LTV > 85), результат решения —
`reject` независимо от пробега. Проверка пробега живёт только в
approve-ветке и не влияет на заявки, которые по LTV получают `reject`.

Источник: открытый вопрос в `intent_MILEAGE.md:46-49`,
`grill_MILEAGE.md:41-49` (в. 4 «до решения действует допущение плана:
reject остаётся reject при любом пробеге; проверка живёт внутри
approve-ветки `decide()`»), владелец — риск-менеджмент. До решения
риск-менеджмента это поведение пинируется тестом.

### REQ-MILEAGE-06 — диапазон действия проверки 400 001…500 000

Проверка пробега действует на заявки с пробегом в диапазоне
400 001…500 000 км включительно. Заявки с пробегом > 500 000 км
по-прежнему отклоняются валидатором с ошибкой по полю `mileage` и до
расчёта решения не доходят.

Источник: `intent_MILEAGE.md:26-30`, `grill_MILEAGE.md:53-60` (в. 5
«`max_mileage_km` = 500 000 не меняется; 400 001–500 000 → review, свыше
500 000 — по-прежнему ошибка валидации 422»), число 500 000 —
`backend/config/rules.php:23`.

### REQ-MILEAGE-07 — сохранение LTV-порогов решения

Правило пробега применяется поверх существующих LTV-порогов и не
изменяет их: `approve_max = 60.0`, `review_max = 85.0`.

Источник: `intent_MILEAGE.md:32-33`, `backend/config/rules.php:44-45`.

### REQ-MILEAGE-08 — лимит при review равен нулю

При результате решения `review` (включая случай, когда `approve`
понижен до `review` из-за пробега по REQ-MILEAGE-03) поле `approved_limit`
в ответе сервиса равно нулю. Лимит выдаётся только при `approve`.

Источник: `intent_MILEAGE.md:34-35`, `backend/src/Domain/AssessmentService.php:39`.

### REQ-MILEAGE-09 — отсутствие поля mileage — ошибка валидации

Если поле `mileage` отсутствует во входном payload заявки, валидатор
возвращает ошибку валидации по полю `mileage` (HTTP 422), и заявка до
расчёта решения не доходит. Это требование фиксирует текущее поведение
валидатора до решения открытого вопроса о трактовке «отсутствующего
поля».

Источник: `intent_MILEAGE.md:36-38`, `grill_MILEAGE.md:31-39` (в. 3
«До решения — текущее поведение (422), пинируется тестом»),
`backend/src/Domain/ApplicationValidator.php:43-46`.

## 5. Критерии приёмки

Формат: Given / When / Then. Базовый валидный payload для всех AC —
минимальные поля, проходящие валидацию (`vin`, `year`, `mileage`,
`market_value`, `requested_amount`, `term_months`), см.
`tests/Unit/AssessmentServiceTest.php:32-43`.

### AC-MILEAGE-01 — пробег 399 999 км не понижает approve (к REQ-MILEAGE-02, REQ-MILEAGE-03)

Given: заявка с LTV в approve-зоне (`market_value = 1 000 000`,
`requested_amount = 500 000` → LTV = 50.0) и `mileage = 399 999`.
When: сервис выполняет предварительную оценку.
Then: результат `decision = "approve"`, `approved_limit = 500 000`.

Источник чисел: 399 999 — граница ниже порога из REQ-MILEAGE-02;
500 000 / 1 000 000 — `tests/Unit/AssessmentServiceTest.php:46-53`
(тот же сценарий LTV = 50.0).

### AC-MILEAGE-02 — пробег ровно 400 000 км не понижает approve (к REQ-MILEAGE-02)

Given: заявка с LTV в approve-зоне (LTV = 50.0) и `mileage = 400 000`.
When: сервис выполняет предварительную оценку.

### AC-MILEAGE-04 — пробег 500 000 км понижает approve до review (к REQ-MILEAGE-03, REQ-MILEAGE-06)

### AC-MILEAGE-05 — пробег выше 500 000 км — ошибка валидации (к REQ-MILEAGE-06)

Given: заявка с `mileage = 500 001` и остальными валидными полями.
When: сервис выполняет предварительную оценку.
Then: валидатор бросает `ValidationException` с ошибкой по ключу

Источник: `backend/src/Domain/ApplicationValidator.php:43-46`,

### AC-MILEAGE-08 — пробег ровно 400 000 не перекрывает reject (к REQ-MILEAGE-02, REQ-MILEAGE-05)

### AC-MILEAGE-09 — отсутствие поля mileage — ошибка валидации (к REQ-MILEAGE-09)

Given: payload заявки без поля `mileage`, остальные поля валидны.
When: сервис выполняет предварительную оценку.
Then: валидатор бросает `ValidationException` с ошибкой по ключу
`mileage`; результат решения не возвращается.

Источник: `backend/src/Domain/ApplicationValidator.php:43-46`
(`$mileage = (int) ($payload['mileage'] ?? -1); … if ($mileage < 0 …)`),
`grill_MILEAGE.md:31-39`.

### AC-MILEAGE-10 — пустая строка mileage — текущее поведение до отдельной задачи (к REQ-MILEAGE-09)

Given: payload заявки с `mileage = ""`, остальные поля валидны.
When: сервис выполняет предварительную оценку.
Then: `null`/пустая строка приводятся валидатором к 0, проходят
валидацию, и при LTV в approve-зоне сервис возвращает
`decision = "approve"`. Это текущее поведение пинируется тестом и
будет изменено отдельной задачей по нормализации «неизвестного» пробега
(см. раздел «Не входит»).

Источник: `backend/src/Domain/ApplicationValidator.php:43-46`,
`intent_MILEAGE.md:60-67` («`null`/пустая строка не должны превращаться
в 0 и давать approve… реализация вынесена в отдельную задачу… в этом
изменении approve с null-пробегом временно остаётся возможен»),
`grill_MILEAGE.md:65-71`.

### AC-MILEAGE-11 — сохранение LTV-зон (к REQ-MILEAGE-07)

Given: заявки со значениями LTV на границах LTV-зон:
- LTV = 59.99 → approve-зона;
- LTV = 60.00 → review-зона (граница `approve_max`);
- LTV = 85.00 → review-зона (граница `review_max`);
- LTV = 85.01 → reject-зона;
и пробегом ниже порога (`mileage = 1 000`).
When: сервис выполняет предварительную оценку для каждой заявки.
Then: решения соответственно `approve` / `review` / `review` / `reject`;
правило пробега не меняет результат.

Источник чисел 60.0 и 85.0: `backend/config/rules.php:44-45`
(`approve_max = 60.0`, `review_max = 85.0`),
`backend/src/Domain/DecisionEngine.php:32-40`.
